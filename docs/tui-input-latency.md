# Coding 输入延迟调查（2026-10-21）

## 定位

实际路径是 `TUI._input_loop` → `InputPanel.handle_input` → 请求绘制 →
`InlineLayout.render` → `Transcript.render` → 各消息组件 → main-buffer 差分绘制。
不能因为最终只输出变化行，就认为消息排版也只计算变化行。

使用 Coding 的实际 ChatLog、User/Assistant/Tool 组件、编辑器和 Footer，在同一进程中
分别构造 0/20/100/300 轮历史，每轮含用户消息、Markdown 回复和工具输出。
在固定宽度 174 下先预热，再对五次普通字符输入与布局分别取中位数。
以下是本机的合成重现，不是用户现场端到端键盘延迟或真实终端输出耗时：

| 历史轮数 | 修复前按键处理 ms | 修复前布局 ms | 修复后按键处理 ms | 修复后布局 ms |
| --- | ---: | ---: | ---: | ---: |
| 0 | 0.115 | 0.128 | 0.116 | 0.120 |
| 20 | 0.149 | 9.801 | 0.121 | 0.859 |
| 100 | 0.151 | 48.100 | 0.143 | 3.928 |
| 300 | 0.153 | 142.885 | 0.125 | 10.763 |

普通字符处理本身不是该重现的瓶颈。Profile 显示重复的 role gutter、ANSI/Unicode
宽度计算、背景填充、工具标题/全文清理与摘要在每帧遍历历史时重新执行。

## 修复边界

- UserMessage 和 NormalMessage 缓存最近一次宽度的最终装饰行；更新文本、失效或宽度变化时重建。
- 父子通信记录缓存最近一次文本/身份/状态/详情模式/宽度的排版，保留原始详情及导出。
- 工具输出的清理、预览和宽度排版复用未变化结果；宿主复用已更新的工具标题。
- 每个组件只保留一份最近缓存，不按所有历史宽度或每次输入无限累积。
- 流式结果、终态、展开/收起、主题失效、ASCII 模式及宽度变化仍需刷新。
- 图片仍按原渲染路径调用，不把终端图像传输误当成普通静态文本缓存。
- 不移除按键处理、审批保护、补全、主草稿保护、历史或消息；不改变任何权限和运行时生命周期。

## 另发现但未在本次改动中修复的补全路径

只读审计与实际编辑器基准还发现：以 `/` 开头且不含空白的草稿，Coding 的
`list_commands()` 会同步读取技能目录及 `SKILL.md`，未变化的补全 poll 也会重复读取。
100 个测试 skill（每个正文 4KiB、热文件缓存）时，一次编辑约 82.56ms，
一次未变化 poll 约 41.12ms；这与普通消息输入的历史排版瓶颈是两个独立问题。
这部分尚未修复，不能把本次缓存优化报告为已经消除了 slash 输入的全部卡顿。

普通文本路径的编辑器测试未观察到同步文件 IO/模型/权限重配置；文件及参数补全
主要使用既有后台 worker。另有重复补全更新和长行 token 扫描，仍需单独收敛，
尤其不能用丢弃动态注册身份/owner fence 或绕过命令实际授权来换性能。

补全基准脚本及记录：`/tmp/xdog_input_bench.py`、`/tmp/xdog_input_bench.out`。

最终合并灰色预览说明后的相关回归：1028 passed（10.89s），日志
`/tmp/xdog-input-and-preview-regression.log`。Ruff、本次文件 diff-check 与
三包 strict mypy（296 源文件）通过。父子通信预览尾部的说明文本及其折行使用
当前主题的 dim 样式，正文、完整详情和导出不受影响。
