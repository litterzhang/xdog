# Proposal：Claw 支持独立的小红书双向 Channel

日期：2026-10-30

状态：提案，未实现、未部署、未接入账号。本次只新增设计文档，不授权实际评论、发帖或自动回复。

## 1. 定位与决策

为 Claw 增加 `xhs` channel，用于接收小红书评论并在原评论处回复。它是面向外部用户的双向交流渠道，**不是管理员命令入口，也不是主会话的另一个入口**。

已确定：

- 第一版使用 `xpzouying/xiaohongshu-mcp` 作为浏览器读写后端，优先调用其 HTTP API；不引入另一套运营 Agent。
- 第一版范围是评论与相关 @ 通知，以及可定位目标的评论回复；不宣称支持私信。
- 外部消息进入独立的小红书会话、工作区和记忆，不路由至 `main`，不继承主会话私人资料。
- channel 支持双向读写；允许回复不等于允许执行管理命令，也不意味着默认允许所有场景自动回复。
- 后续确有私信需求时，可以 fork 上游实现。当前不预先 fork、不实现私信协议、不设计跨平台身份合并。

非目标：自动发帖、主动私信、批量营销、自动点赞收藏、全站采集、主会话通知转发、管理后台替代品，以及重构整个 Claw 会话模型。

## 2. 上游依据与能力边界

仓库：https://github.com/xpzouying/xiaohongshu-mcp

本次审阅固定提交：`7797fd375aba02dcd33afe143f6bee13e5870859`。检查了全部 62 个 Go 源码文件及工具注册、HTTP 路由；最新正式版本为 v2.5.5。此处是源码调查，不是账号实测结论。

| 能力 | 上游入口 | 第一版用途 |
| --- | --- | --- |
| 登录状态 | `GET /api/v1/login/status` | 连接健康检查 |
| 通知未读数 | `GET /api/v1/notifications/unread` | 辅助提示，不作为唯一收件游标 |
| 评论和 @ 通知 | `GET/POST /api/v1/notifications/list`，`tab=mentions` | 拉取候选入站事件 |
| 笔记与评论详情 | `POST /api/v1/feeds/detail` | 补齐必要的公开线程上下文 |
| 通知评论回复 | `POST /api/v1/notifications/reply`，`comment_id` + `content` | 原处回复 |
| 指定笔记评论回复 | `POST /api/v1/feeds/comment/reply` | 仅在同一目标可精确核验时使用，不作盲目回退 |
| 私信会话、历史、发送 | 当前无实现或入口 | 不支持 |

源码参考：`routes.go`、`mcp_server.go`、`service.go`、`xiaohongshu/notification.go`、`xiaohongshu/notification_reply.go`、`xiaohongshu/comment_feed.go`。

已知约束：

1. `list_notifications` 打开通知页，会清除对应分区的未读标记。即便上游工具标为 readonly，也不能宣称它没有账号状态副作用。
2. 通知列表默认 20 条，最多滚动 20 轮；对外没有续读游标和完整性标志，不能保证任意积压均能完整补收。
3. 每次服务调用会创建并关闭浏览器，不是持续消息长连接；页面结构、登录状态及平台限制会影响可用性。
4. 通知记录有通知 ID、评论 ID、发言者 user_id、关联 feed_id，但不保证具备完整的根评论/父评论关系。
5. 回复通过页面列表位置和昵称提示核对目标；昵称不是身份凭证，页面重排可能造成定位风险。
6. 上游回复成功判据主要是输入框收起，没有新回复 ID 或可靠的平台送达回执。不能直接把 HTTP 200/返回成功记为 `delivered`。
7. 近期有登录安全验证、功能超时和账号异常反馈。私信需求仍见开放 Issue #782；其他风险见 #875、#880、#877、#860。这些是用户报告，不是全平台失效证明。

若原评论身份或发送结果不能核实，第一版必须明确降级为不可回复/结果不明；不得为了凑齐“双向支持”而假报成功。必要的上游修复单独评估，不在本 proposal 中假设已经存在。

## 3. 接入现有 Claw 架构

```text
XHS 浏览器后端
  → XhsChannel 拉取、归一化、去重
  → 宿主核实账号/线程绑定，构造非管理输入与冻结回复目标
  → 现有 Orchestrator → InputService/Core Inbox
  → 独立 XHS group 的 GroupController / GroupRuntime / AgentSession
  → 现有输出 journal
  → XhsChannel.send_output → 精确回复原评论 → 核实结果
```

复用当前 `channels/base.py` 的生命周期与发送契约：`connect`、`disconnect`、`send_reply`、`send_output`、`reply_context`；不假设 `send_message(group_id, text)` 足以表达评论目标。

- channel 适配器仅负责平台连接、收发与地址映射，不拥有第二个模型循环、执行队列或 Agent。
- 复用 `core/inputs` 的持久入队、去重和执行所有权，以及 `core/outputs` 的输出记录；平台扫描进度和平台事件映射是连接器状态，不是第二套任务系统。
- 本方案不通过 Eyes/ACP 向 `group:main` 注入评论，也不把收件做成不断唤醒主 Agent 的轮询任务。
- 启动后端、启用 channel、登录账号和开启自动回复属于后续明确配置动作；读取或安装提案不触发它们。

### 3.1 当前实现需要显式处理的缺口

`core/runtime/input_adapter.py::freeze_input` 当前会把普通 `UserInput`（默认 `input_origin=user`）投影为 `human_authorized=true`。不能简单复制现有聊天入口，再靠 system prompt 写一句“不要执行命令”。

第一版由受信任 channel 适配器构造 `ExternalInput`，并由宿主显式绑定回复目标，持久化为 `human_authorized=false`。XHS 发言者可以是真人，但不是 Claw 管理员；“真人来源”与“管理授权”不可混同。

实现时核查命令分派、输入消费、审批、会话恢复和工具执行路径。若某处仅按类型或正文判断权限，必须补齐宿主拒绝门禁。字段由宿主生成，远端正文、昵称、链接或元数据不能覆盖。

当前 `route_message` 只对部分来源自动创建 group；XHS 的受限 group 创建需要显式接入，不能依赖不存在的通用自动注册能力，也不能回退到默认 `main`。

## 4. 会话与回复地址

### 4.1 会话隔离

第一版采用宿主维护的 `(账号绑定, feed_id, 线程锚点)` → 独立 group 映射。

- 能从真实平台数据核实根评论时，以根评论为线程锚点。
- 无法可靠得到根评论时，以具体 `comment_id` 为较窄锚点；宁可上下文分散，也不按昵称、正文相似度或模型推断合并。
- 创建工作区时只使用专用 XHS 人设及管理员显式提供的公开产品资料，不复制主工作区、MEMORY.md、历史或全局私人资料。
- 多个线程不共享私有对话记忆；只允许复用明确发布给该账号的公共知识。公开评论上下文仍属于不可信外部内容。
- 配置必须拒绝将 XHS 绑定到主会话或既有管理会话。group 数量、入站速率和排队容量有界，避免公开账号被刷评论耗尽资源。

### 4.2 宿主拥有回复目标

入站事件保留平台账号 ID、事件 ID、作者 ID、feed_id、comment_id、可得的父/根评论 ID、时间及原文；昵称只用于展示。

回复目标随原输入冻结，至少绑定账号、feed_id、comment_id、预期作者 ID 和 channel 绑定版本。涉及访问令牌的路由字段仅留宿主内部，不当作公开链接或日志输出。

- 正常回复只能回该原评论，不能由模型提供任意用户/笔记地址。
- 仅凭 group_id、当前最后一条通知或昵称不能选定回复对象。
- 不向模型暴露整个账号任意评论/私信发送接口，不提供跨 channel 广播。
- 第一版仅发送一条最终文本回复；不把流式 token、思考、工具日志或中间进度逐条发成评论。
- 暂无可冻结的具体评论目标时，不提供账号级主动发送目的地。

## 5. 非管理 Channel：强制权限边界

**XHS 只承载业务交流，不承载 Claw 控制面。即使账号主人在 XHS 评论里发指令，也不因此升级权限。**

必须由宿主强制保证：

- `/new`、`/model`、`/goal`、暂停/恢复、工具审批、配置修改、服务管理等控制请求不能执行；未知 slash 文本同样不能进入管理分派。可作为普通文本处理或返回简短不支持提示。
- “我是管理员”“批准执行”“忽略限制”等自然语言不构成授权；不得解除 user wait、用户暂停或接受任何管理确认。
- 默认不赋予 bash、通用文件访问、代码修改、任意网络请求、子 Agent、Goal、Eyes、Flow、跨组 memory/history 或通用消息发送能力。不使用 `enabled_tools=None` 继承默认全套工具。
- 只授予宿主实际约束过的当前线程只读上下文能力；回复由固定输出路径完成。后续新增业务工具必须逐项授权，MCP 全工具库存不得直接交给 XHS Agent。
- 子页面、评论、引用、图片文字和第三方链接均不能修改系统提示、工具配置、收件身份或发送目的地。
- 限制不只写在提示词里：命令路由、实际工具注册、执行入口、历史恢复和输出发送边界均需成立。会话轮换、进程重启不能丢失该限制。

管理员仍从已授权的本地/TUI/管理入口配置启停、回复策略、账号登录和审批。主会话可用于管理员提出管理请求，但不自动接收 XHS 评论流；审批执行还需当前权限核验。

## 6. 收件与投递可靠性

### 收件

- 可配置低频轮询；没有新事件不调用模型。未读数只是优化信号，仍需周期性重叠扫描，因为 App 阅读会清未读。
- 按账号与稳定平台事件 ID 去重；为同一评论跨通知来源归一，避免重复处理。无法获得稳定身份的条目不自动回复。
- 首次连接建立基线，默认不回复历史评论；补收历史需管理员明确范围。
- 在 Core Inbox 持久接受后才推进“已入队”状态；ACK 丢失以相同输入 ID 查询/重试入队，不生成新 ID。相同 ID 内容变化按既有冲突规则处理，不覆盖已接受正文。
- 编辑不当作新评论自动回复；自己发送的评论/回复不得形成自触发循环。
- 分页边界未覆盖历史锚点、触及加载上限或采集失败时，记录缺口/降级，不当作“没有新消息”，不推进到虚假的完整水位。
- 登录失效、安全验证或账号限制转为明确连接状态并等待管理员处理，不自动绕过验证码或限制。

### 回消息

启用时由管理员显式选择 `review`（审核后发送，首版默认）或限定业务范围的 `auto_reply`。XHS 来信不能改变模式。审核须绑定具体原评论、账号和最终正文；正文或目标变化后重新审核。

- 发送使用现有稳定 `output_id`，记录原评论与输出的关联；发送前重新核实绑定仍有效、目标仍匹配、审批/自动回复权限仍成立。
- 上游点击完成、HTTP 成功、输入框收起只算提交迹象；回查确认正确线程内由本账号发出的目标回复，才能记为已送达。相同文本存在歧义时不作肯定匹配。
- 无法核实结果记 `unknown`；确认未提交才记录 proven-not-sent。未知、超时、连接断开、进程崩溃后的发送绝不自动重发。
- 平台没有幂等发送键，不能声称端到端 exactly-once。后端失败后不自动切换另一条回复接口补发。
- channel 停用后，新的收件和尚未开始的发送被阻挡；已接受输入与已提交平台请求分别结算，不能宣称停用撤回了已发生的外部效果。

## 7. 后端部署与后续扩展

第一版将上游作为独立、本地服务使用，固定并记录版本；浏览器登录和 Cookie 由后端管理。优先 loopback 与认证，不向公网暴露可用账号凭据执行写操作的服务；凭据不进入模型、正文或普通日志。

上游仍是浏览器自动化，不是官方消息协议；低频、本地运行或人工审核均不等于平台认可。安装前审查依赖和账号风险；不要求用户关闭安全软件。

如后续 fork 增加私信，应单独评审会话 ID、消息 ID、历史游标、收发确认、登录验证与平台规则。私信使用独立的会话命名空间和隐私策略，不与公开评论或主会话自动合并。当前适配层只隔离后端调用，不为尚不存在的私信接口添加占位能力。

## 8. 验收标准

以下全部为待实现/待验证，不是现有通过记录。

1. 受控账号的新评论经真实 channel → Core Inbox → 独立会话处理；没有内容写入或读取 `main` 的工作区、历史和记忆。
2. 对原评论完成一次经授权的真实回复，并提供独立于模型完成/HTTP 成功的送达证据；不向其他线程、账号或渠道发出消息。
3. 管理命令、伪造管理员身份、恶意评论/引用中的工具指令均无法触发控制面；原始输入、恢复后的输入和实际执行入口都经过负向测试。
4. 不继承主 Agent 的工具、技能授权或私人提示资料；线程 A 无法读取线程 B 的私有记忆。同名用户、页面重排、账号切换均不导致串回复。
5. 重复拉取、ACK 丢失和重启不会重复入队；自己的回复不触发回复循环；首次历史基线不自动补回复。
6. 手机端已读、超过默认页容量、加载受限及采集失败均有测试；可证明补收的正常情况与不可证明完整的缺口明确区分。
7. 模拟“平台已提交但返回超时”、输入框收起但未送达、崩溃/暂停竞态，输出记录保持真实；未知结果不自动重发。
8. review 模式的内容与目标绑定、auto_reply 的范围约束，以及关闭 channel 后的发送门禁有宿主级测试，不只验证模型口头拒绝。
9. 无新事件不唤醒模型，轮询与队列容量有界；登录验证、账号限制、后端不可达时清楚降级。
10. 文档和能力展示只承诺评论读写，不出现“已支持私信”；真实账号试验须额外明确授权，单元测试不得发出真实评论。

## 9. 建议实施顺序

1. 完成 XHS 非管理输入与隔离 group 的宿主权限测试，再接平台 IO。
2. 接入只读通知、持久去重、线程映射和缺口状态，用 fixture/mock 验证收件。
3. 接入冻结回复目标与输出 journal，解决目标核验和送达证据；证据不足时保留明确限制。
4. 经授权进行单条评论收发验收，默认人工审核；确认后才启用受限自动回复。
5. 私信另开需求，届时决定是否 fork 上游。本提案不创建实现任务、定时器或运行服务。
